# Audit, November 2026: what was checked, what was broken, what was fixed

17 Nov 2026. The bug hunted for: a feature that silently shows n/a, empty, stale or wrong data in
real use (after the close, at weekends, during a provider outage, on Streamlit Cloud's UTC clock)
while the tests pass. The trigger was the Research Notes "app score n/a" bug fixed in #364.

## How it was checked

- Every page 02–15, every view, the alert jobs (`alerts/`), the workflows, `scripts/` and
  `trade_store.py`. Each data path was traced from the writer (warm jobs, alert jobs, KV keys and
  their `user_id`) to the reader (freshness rules, ticker format, IST vs UTC, empty state).
- Every fixed bug has a test that fails on the old code and passes on the new one.
- Every PR ran the full suite (`pytest -m "not slow"`) and the page smoke tests.
- `verdict-regression-reviewer` ran on the fundamentals / thesis change: no posture or confidence
  changed.
- Not in scope: Command Centre (page 01, another session was editing it). Research Notes was left to
  #364.

**Status words used below:**
- **Fixed #N**: bug reproduced in a test and fixed in that PR.
- **No bug found**: code read end to end, tests exercise it; NOT run against live data.
- **Not verified**: needs live NSE / Yahoo / Angel One / a broker login, so it could not be
  exercised here.
- **Open**: a real issue that is not fixed yet; the reason is given.

Nothing below is marked "works" on the strength of having been looked at.

## Follow-up, 17 Nov afternoon: Angel One 403s, NSE announcements 403s, movers radar cap

These come from the Market Alerts logs: run 44058454779 (15:15 IST), compared with runs 44028027712
(11:30 IST) and 44056173671 (15:00 IST).

### 1. Angel One candle history: HTTP 403 (fixed in #376; cause most likely a rate limit, not verified)
- **What the logs show:**
  - At 15:15, LENSKART, SGMART and MCX each got a 403 on an ~18-day request. A short window like
    that is a single request, so the window size is not the cause. Yahoo then served the prices,
    and the 15:15 recap was correct.
  - At 15:00, INDIAGLYCO, REFEX and SOUTHBANK got 403s; SOUTHBANK was tried twice.
- **Why it most likely happened:** the API returns 403 rather than 401, which suggests the session
  token was still valid; a bad session would normally return 401.
  - Angel One's candle limit is per API key. **Warm Top Picks ran from 09:45:10 to 09:53 UTC
    (15:15–15:23 IST) on the same key**, scanning ~750 names, while Market Alerts asked for candles
    at 09:45:50.
  - At 15:00 no warm job was running. The dashboard on Streamlit Cloud uses the same key and is
    the likely other user.
  - The 16 Nov price-store run showed 403s with "access rate" in the body.
  - The old log printed only the status, so the reason could not be confirmed. That is fixed below.
- **Fixed:**
  - The 403 body is now read and logged as `rate limit` / `session expired` / `forbidden`, with
    Angel's errorcode and message.
  - A rate limit triggers a back-off: 60 s, doubling to 5 min, and reset by a successful call.
    During it, every further symbol goes straight to the next data source with no Angel call.
  - An expired session forces a fresh login.
  - The fallback warning now says why Angel returned no data.
  - The `data-provenance-auditor` reviewed this. Its point (don't treat "Invalid symboltoken" as
    an expired session) is included. It could not reach any provider from this sandbox.
- **What the owner may need to change on the Angel One side:** nothing is required for
  correctness, because Yahoo covers the gap.
  - If the next logs show `rate limit`, create a second SmartAPI app (API key) for the GitHub jobs
    and store it as the `ANGEL_API_KEY` Actions secret. The dashboard keeps its own key, so the two
    stop sharing one limit.
  - If they show `forbidden` with an errorcode instead, check the key's permissions for historical
    data in the SmartAPI dashboard.
- **Not fixed (each job has its own back-off):** another job on the same key does not see this
  job's back-off. Staggering the cron-job.org trigger for Warm Top Picks by a few minutes away from
  Market Alerts' :00 / :15 / :30 / :45 would also reduce collisions.

### 2. NSE announcements: HTTP 403 (fixed in the main session, branch `claude/nse-403-retry`: logs the warm-up status, and on a 401/403 clears cookies, re-warms and retries once; the BSE fallback install merged as #375)
- **The cookie warm-up and browser headers are used on GitHub's runners.** The API call goes
  through `nse_corp_info._ensure_session()`: Chrome User-Agent, Referer, and a homepage GET first.
- **The block is intermittent, not a header problem.** The same job read announcements fine at
  11:30 IST ("18 new filers") and 15:00 IST ("33 new filers"), then got 403 at 15:15 on both the
  API and the RSS archive. Each run gets a different runner IP, which fits Akamai blocking some
  datacenter IPs.
- **Not verified live:** this sandbox cannot reach NSE either.
- **Suggested to the main session:**
  - log the warm-up GET's own status;
  - on a 403, start a fresh session (new cookies), re-warm and retry once before falling back;
  - keep BSE as the fallback, which is the main session's current fix.

### 3. Movers radar: daily cap (fixed in #376)
- **The real problem was pacing, not the size of the cap.** One message per 15-minute run spent all
  6 by about 11:00 IST; from 11:30 every run logged "daily cap of 6 radar messages reached", so
  afternoon moves were never alerted.
- **Fixed:** the same 6 are released one per window: 09:45, 10:30, 11:30, 12:30, 13:30 and 14:30.
  - An unused window carries forward.
  - Movers held by the pacing are not marked as sent, so they stay eligible.
  - A batch with a bullish Tomorrow's Watchlist name is never held back by the pacing; the daily
    cap still applies.
- **Ranking inside a message is unchanged:** Tomorrow's Watchlist names first, then the bigger
  market-cap tiers. Holdings are covered by the separate holding guard.
- **Owner decision, not changed:** whether to raise the cap above 6, or to also put holdings that
  are rising first in the radar.
